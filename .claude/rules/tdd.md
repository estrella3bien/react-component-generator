# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 프로젝트의 CLAUDE.md 또는 AGENTS.md에 TDD 관련 지침이 있으면 그것을 우선한다. 이 파일은 fallback이다.

---

## 적용 기준

### TDD 필수 대상
- 비즈니스 로직 (계산, 상태 전이, 규칙 검증)
- API 엔드포인트 핸들러
- 유틸리티 함수
- 버그 수정 — **버그를 재현하는 실패 테스트를 먼저 작성**

### TDD 불필요 대상
- TypeScript 타입/인터페이스 정의
- 설정 파일 (vite.config, tsconfig, eslint 등)
- 순수 UI 렌더링 (스타일, 레이아웃, 정적 마크업)
- SQL 마이그레이션 스크립트

---

## RED → GREEN → REFACTOR

### RED: 실패하는 테스트 작성
- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 눈으로 확인**한다.
- 실패 이유가 반드시 **"기능 미구현"** 이어야 한다. 문법 오류나 import 누락으로 실패하면 RED가 아니다.

### GREEN: 통과시키는 최소 코드 작성
- 테스트를 통과하는 **가장 단순한 코드**만 작성한다.
- **YAGNI** — 지금 테스트가 요구하지 않는 코드는 작성하지 않는다.
- 신규 테스트와 **기존 테스트 전체**가 통과하는지 확인한다.

### REFACTOR: 동작 유지하며 코드 개선
- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **Green 상태를 유지**한다 — 리팩터 중 테스트가 깨지면 즉시 되돌린다.
- **새로운 동작을 추가하지 않는다.** 추가하고 싶으면 다음 RED로 넘어간다.

### 반복
다음 동작에 대한 RED로 돌아간다.

---

## 삭제 강제 규칙

테스트 없이 프로덕션 코드를 먼저 작성했다면:

1. **그 코드를 삭제한다.**
2. RED부터 재시작한다.

**"참고용으로만 남겨둔다"는 없다.** 파일에 남아있는 코드는 프로덕션 코드다.

## 변명 차단

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 불필요하다" | 단순한 코드일수록 테스트 작성 비용이 낮다. 단순함은 테스트를 생략할 이유가 아니라 더 쉽게 쓸 수 있는 이유다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 코드가 동작하고 나면 테스트를 추가할 동기가 사라진다. |
| "시간이 없다" | TDD 없이 작성한 코드는 디버깅과 회귀에 더 많은 시간을 쓴다. 지금 아끼는 시간을 나중에 두 배로 갚는다. |
| "코드를 삭제하면 낭비다" | 테스트 없이 작성한 코드는 검증되지 않은 코드다. 버리는 것이 낭비가 아니라 그 상태로 남기는 것이 낭비다. |
| "프로토타입이라 괜찮다" | 프로토타입은 버린다. 프로덕션에 들어가는 순간 프로토타입이 아니다. |
